# 全历史样本计数优化

仅优化趋势 `period=all` 的样本数量。7/30/90/180 天、今日及 24 小时窗口继续从分享登记表读取；排行榜内容、检查点、缓存键和 TTL、接口结构、前端交互不变。先前已验证的排行榜 SQL 改写一起发布，详情见 [趋势查询优化](trend-query-optimizations.md)。

## 数据与读取

迁移 `0003_share_count_kind.sql` 新建：

- `my9_share_count_kind_v1`：每个 kind 一行 `share_count`，当前预计 11 行；WITHOUT ROWID 主键，不给历史事实表新增索引。
- `my9_share_count_state_v1`：一行就绪状态；表名 v1 同时限定实现版本。
- 5 个登记表触发器：新增、删除、改分类各一个，以及插入/更新发生唯一键冲突时的保护各一个。

有 rollup 检查点时，样本数等于 `kind 总数 - COUNT(created_at > checkpoint.createdAt)`。最早/最新时间仍用原来的 `created_at <= checkpoint.createdAt` 索引端点查询。没有检查点时直接用 kind 总数。三个值在同一条 SQL、同一读取快照中获得；检查点恰好等于分享时间、检查点停在分享中间的旧有行为都保持一致。空分享也计入样本，不从作品槽位数推算分享数。

尾部 COUNT 与两个端点查询都使用已有 `(kind, created_at DESC)` 索引。检查点正常推进、尾部很小时，全历史统计可从每次十几万至几十万行降至个位数读取；检查点长期停滞时尾部会增长，不能保证永久固定读取量。缓存命中的请求不会执行这条 SQL。

## 写入、一致性与回退

数据库触发器和原分享变更在同一事务提交。普通 INSERT 成功后增加一行计数；删除减少；kind 更改对旧、新 kind 各更新一次。普通重复插入失败、失败事务回滚都不留下计数变更。时间、浏览时间和其他字段更新不改总数。

SQLite 的 REPLACE 在 `recursive_triggers=OFF` 时可能不触发被替换行的 DELETE 触发器。保护触发器会在发现 share_id/content_hash 冲突时将 ready 置零：普通 INSERT/UPDATE 报错时该修改随事务回滚；冲突 IGNORE、UPSERT、REPLACE 提交时保留停用状态，之后计数维护暂停，应用自动采用原来的精确查询。无冲突的新行仍可正常使用这些语法。当前应用登记表写入使用普通 INSERT；保护措施主要覆盖维护导入与未来代码。

查询在小表不存在、未 ready、查询失败、计数为负或与空集合端点明显不符时回退到原查询；不会把负数截断为零，不在请求或 cron 中自动扫描回填。不检测任意人工篡改的正数计数或手工删除触发器；直接改小表/触发器必须视作运维操作。

需要回滚读取逻辑时，将 Worker 环境变量 `MY9_TRENDS_ALL_COUNT_SOURCE=registry` 后重新发布，计数维护仍继续。也可回退 Worker 到旧版本，新增 schema 与旧版本兼容。数据库紧急停用只需 `UPDATE my9_share_count_state_v1 SET ready=0 WHERE id=1`（一行写入），但这会同时暂停计数维护，之后**不能直接置回 1**。恢复必须在一次已评估并获授权的原子事务里清空小计数表、重新 GROUP BY 初始化、再置 ready=1，并核验触发器。此操作不会由程序自动触发。

## 迁移与成本边界

使用 Wrangler migration 或等价的 D1 单次事务提交完整 SQL，并在同一事务写入 `d1_migrations`。不要把文件拆成多次独立请求。表、触发器、初始化以及 ready 一起生效，期间发生的分享写入由数据库串行化；失败时整体回滚。旧 Worker 可先使用新 schema，再由推送 main 触发既有 GitHub Actions 自动构建/部署。

本地自动 schema 初始化不包含这次回填；开发库运行显式 migration 后使用小表，未迁移时走旧查询。生产只执行尚未登记的 `0003`，不重建趋势，不改写历史分享和槽位，不为大表创建索引。

预算基于约 96.2 万份分享、11 种 kind：初始化扫描一次约 96.2 万行，写 11 行计数及少量状态/schema/迁移记录；线上全量核验再扫描一次，自动构建首页计数可能另扫描一次。给此次迁移、验证和自动构建预留合计 **500 万读取 / 1,000 写入** 上限，按超额单价折算约 **$0.006**，套餐内通常没有新增账单。单次初始化写入应远低于 1,000 行，不会达到百万级。

日常每份新增分享通常多一次计数行写入，首次出现的 kind 会创建该行；改分类多两次、删除多一次。按此前 30 天 14,273 份新增估计，保守按 1–3 次计费写入计为约 1.4–4.3 万额外写入/月，全部超额时约 $0.014–0.043。保护触发器还有主键/唯一索引探测读取。收益主要是降低扫描、计算和数据增长后的压力，不代表当前套餐内现金支出会相应减少。
