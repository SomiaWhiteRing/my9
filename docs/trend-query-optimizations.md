# 趋势查询优化（2026-09-18）

本文记录第一阶段的读取 SQL 优化，目标是减少趋势查询的计算和排序成本。该阶段没有新增汇总表、索引、迁移、定时任务或持久缓存写入；现有缓存 TTL、统计时间窗口、汇总检查点和前端交互均沿用原实现。随后获准实施的全历史计数小表见 [全历史计数优化](all-history-count-optimization.md)，两阶段代码一起发布。

## 改动与等价性

- 样本统计：在同一条 SELECT 中分别执行 COUNT，以及利用既有 `(kind, created_at DESC)` 索引定位最早和最新记录。三个子查询使用相同的 kind、起止时间和检查点条件，并共享 SQL 语句的读取快照。空集合仍返回 `0 / null / null`，时间边界仍包含等于边界的记录。COUNT 仍然扫描匹配行，因此此项主要减少 SQL 计算时间，不会消除计费读取；两个端点查询通常增加两行读取。
- 总榜：分页之前继续排除缺失作品维度的记录，仅携带 kind、subject_id 和 count 排序；选出本页结果之后再加载名称、封面等信息。排序、分页边界和返回编号不变。最后使用 CROSS JOIN 固定从已选中的结果查找维度，防止窄时间窗口触发维度全表扫描。每页至多增加 20 次维度读取。
- 分类榜：先在窄记录上计算完整分类总数和分类内排名，再保留每类前 5 名进行分类 DENSE_RANK。每个非空分类至少保留一行，分类排序所用的总数、标签及其不同取值集合均不变，所以前 20 类的选择与原 SQL 一致。漫画、轻小说过滤及“未分类”的判断不变。名称和封面只在选出结果后加载。
- 年份、年代榜：完整桶总数和桶内排名仍按全部符合条件的作品计算，年份过滤与排序不变；只有最终作品需要加载名称和封面。最终维度关联同样固定为从排名结果查找，额外读取数量等于返回作品数。

第一阶段未包含“增量统计汇总”；下表仅衡量 SQL 改写，不能将第二阶段的“减少 99% 全历史统计扫描”作为这些改写的收益。窗口统计继续使用这里的查询，不增加窗口汇总表。

## 只读核验

从当前 TypeScript 和修改前 Git 版本提取实际 SQL，通过 D1 SELECT 做有界对照；没有调用会初始化 schema 的应用入口，也没有新增测试文件或运行 UI/浏览器测试。所有核验 SQL 的 `rows_written` 均为 0。

最终版本核对了 17 组：10 组排行榜及 7 组样本统计。排行榜覆盖 anime/manga/lightnovel 分类、game 年份与年代、anime 历史年份、第一页/第五页和空结果；统计覆盖有/无检查点、全历史/滚动窗口、相等边界、倒置边界及未来空窗口。返回数组的内容和顺序（JSON SHA-256），以及样本数量和起止时间，都与旧查询相同。

以下为一轮最终查询先执行、旧查询后执行的线上只读测量。时间受缓存、当时负载影响，不是完整页面延迟或稳定性能承诺。

| 查询 | 旧 SQL / 新 SQL 时间 | 旧 SQL / 新 SQL 读取行数 |
| --- | --- | --- |
| anime 全历史样本统计 | 29.57 / 15.29 ms | 310,228 / 310,230 |
| anime 全历史分类榜 | 333.62 / 166.42 ms | 487,420 / 384,587 |
| manga 全历史分类榜 | 329.02 / 143.52 ms | 457,836 / 377,047 |
| lightnovel 30 天分类榜 | 6.74 / 4.62 ms | 9,743 / 9,402 |
| anime 30 天总榜第一页 | 19.98 / 17.85 ms | 47,537 / 47,557 |
| game 全历史年代榜 | 145.19 / 97.74 ms | 183,399 / 183,429 |

小查询并非都加速：game 全历史总榜第五页为 0.47 / 0.71 ms；anime 30 天历史年份榜为 24.65 / 27.19 ms。不能将重查询的改善幅度推广到所有请求。缓存命中路径不经过这些聚合 SQL。

本轮前后对照和调整合计读取约 640 万行；即使全部超出套餐包含量，按每百万读取 $0.001 计算，也约 $0.0064。未发生迁移或生产数据写入。

静态检查：ESLint、TypeScript `--noEmit --incremental false`、`git diff --check`。未运行 UI 测试。第二阶段的本地构建、生产迁移及验证记录见全历史计数优化文档。
