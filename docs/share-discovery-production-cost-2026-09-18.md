## 2. 本次采用的数据逻辑

名称查询保持此前建议的完整名称匹配，输入先 trim，使用参数绑定；每页返回 20 条，查询 21 条判断是否有下一页。沿用数据库默认 BINARY 比较，不额外承诺大小写、Unicode 规范化、前缀或任意包含匹配。

建议的唯一新索引如下，**本轮未执行**：

```sql
CREATE INDEX my9_share_registry_v2_creator_created_share_idx
ON my9_share_registry_v2 (creator_name, created_at DESC, share_id DESC)
WHERE creator_name IS NOT NULL AND creator_name <> '';
```

索引不含 `hot_payload`、封面、浏览量或会随访问改变的时间字段。名称、时间和分享 ID 负责定位及稳定排序，最多 21 行回表取类型，再按分享 ID 查询既有浏览量总表。无需为了 20 个类型值再增加覆盖列；查询预算已包含回表。

后续页使用以下范围条件，避免 OFFSET 随页数增加而多读，也不为 UI 计算全部匹配总数：

```sql
WHERE creator_name = ?
  AND creator_name IS NOT NULL AND creator_name <> ''
  AND (created_at, share_id) < (?, ?)
ORDER BY created_at DESC, share_id DESC
LIMIT 21
```

新索引建成后要用真实 D1 `EXPLAIN QUERY PLAN` 和 `meta` 核验首屏、无结果、同名多页及相同时间戳分页；目前生产结构没有这个索引，不能声称本轮已经测到索引后的完整搜索成本。不要对列使用 `trim(creator_name)`、`LIKE '%...%'`，再套用本报告的预算。

热门榜复用现有 `(kind, view_count DESC, share_id)` 索引。每类取有效分享前 20，共至多 220 个候选，再按 `view_count DESC, share_id ASC` 取全站前 20。全站前 20 必定属于其类别的前 20；SQL 在每类 LIMIT 前检查登记表存在，删除记录不会挤占最终榜单名额。

现有浏览量 rollup 写入时已解析别名并归并到 canonical share ID。快照沿用这一总表语义；不重新汇总访问事件。异常遗留别名/重复浏览量记录若需要修复，应另算清理成本。

每日浏览量汇总成功后，把完整列表及 `viewsThrough` 一起原子 upsert 到 `my9_system_checkpoint_v1` 的一个新 key。沿用已有每日 cron，新增调度次数为 0。刷新失败保留上一份完整快照；快照缺失时返回暂不可用，不让每位访客触发后台刷新。上线时先生成第一份快照。

29.63 MB 模型为 `名称字节 + 分享 ID 字节 + 693,064 × (6 字节时间 + 至多 3 字节 rowid + 至多 6 字节记录头 + 至多 2 字节 payload 长度 + 2 字节页内指针)`。数据库最大 rowid 为 962,175。该模型未包含内部页、页空余、分裂、分配策略，故继续保留 50–100 MB 物理预算，须建成后核验实际差值，不能将预算写成实测值。

只写入新的索引项，不回写 96 万份分享，不处理 861 万槽位。不另加一次“693,064 次索引回填”，避免重复计算。200 万读取包括一次主表扫描和一次索引计数等检查的余量；本轮分析读取单列在第 8 节，不冒充将来迁移消费。

索引建立会占用同库执行时间并可能增加在线延迟；本轮复杂全表统计的 SQL 时间为 9.58 秒，这不是 CREATE INDEX 时间。建索引耗时尚未实测，D1 单条/管理批次 30 秒限制需要在执行时观察，失败不能直接无限重试。空间初始预留是验收预算，不是数学上界。

存储按占用时间持续计费，不是一次性创建费。按近期新署名数量、当前平均项大小和相同页填充水平，额外空间增长模型约 **0.61–1.23 MB/月**；名称分布和页分裂变化会改变它。全部超额时，每增加这样一个月的历史，后续完整月的存储费用约再增加 $0.00046–0.00092。

只有真正 INSERT 的已署名构成才增加新索引项，去重保存命中旧分享不会再增加。删除索引内记录通常再删一个项；变更索引字段按删除旧项、插入新项保守留至多两个逻辑项操作，具体以 D1 meta 为准。模型扩展为 `新增署名 INSERT + 索引内 DELETE + 2 × 索引键变更 + 快照/DDL/重试余量`。修改非索引列、既有浏览量 rollup 不维护这个名称索引。

原方案带九宫格的每次搜索预算 1,500 行，本次纯色类型块方案降为 150 行。SQL 等待时间不等于 Worker CPU；上述 82.29 ms、12.01 ms 的生产 SQL 时间不能拿来代替 5–20 ms 的 CPU 假设。

设 O 为实际默认榜 API 次数，S 为名称搜索及翻页次数，N=O+S：

```text
新增 D1 读取 = 5O + 150S + 50,000
新增 D1 写入 = 10,000（当前正常增长预算；修改、删除、异常重试另计）
新增 Worker 请求 = N
新增 Worker CPU = cN + B，情景 c=5–20 ms，B=3,000–30,000 ms/月
新增日志事件期望 = 0.2N × 每次采样调用的事件数 + 新增后台日志事件
新增持久空间 = 初始 50–100 MB + 后续增长
响应内容预算 = 8,192N 字节，不含 HTTP 开销和前端资源
```

关闭重开或同一页面重复查询命中内存缓存时，不产生 API 请求。表中不假设 CDN/Workers 缓存命中；浏览器取消但服务器已经处理的请求仍需计量。默认只在打开或提交搜索时请求，不能按每次按键请求后继续套用相同 O/S。

## 6. 详情访问带来的消费

类型块使**列表阶段**新增封面/图片代理请求为 0。点击「查看详情」仍会加载现有分享页和封面；若这些是本功能额外引导来的访问，必须计入全站增量。`prefetch={false}` 已用于详情链接，避免列表自动预加载 20 个详情页。

令 D 为额外详情实际请求，I 为它们产生的本站图片代理请求，E 为已有共现按钮产生的额外 API 请求：

| 消费 | 加到上述列表账本的方式 |
| --- | --- |
| Worker 请求 | `D + I + E`，再加重试/额外 API；复用缓存的用户动作不算新请求 |
| Worker CPU | `详情 CPU 总量 + 图片代理 CPU 总量 + E 对应 API CPU`，不能按图片数量推算未测的缓存命中率 |
| D1 | 现有分享读取、作品信息和次数读取按实际 meta；可先按成功 canonical 分享页 **50 行/次**规划，异常 fallback/其他 API 另计，属于模型不是本轮页面实测 |
| 日志 | 对实际进入 Worker 的请求按各路径事件数和采样率累计 |
| 浏览分析 | 合格的 document 导航每次触发既有 `writeDataPoint()`；RSC 导航等可能被现有过滤条件排除，不能简单令所有 D 都等于浏览事件 |
| 浏览量 D1 汇总写入 | 随新增「分享 ID × 日」变化；同一分享同日多次访问合并后只更新一个总数行，不能给每次浏览算一次 D1 写入 |
| 浏览量存储 | 首次被记录的分享增加既有总表记录和索引；不是新增名称索引记录 |
| 外部封面 | 外站直连、本站代理、wsrv.nl/浏览器缓存按实际加载路径统计；列表不调用这些服务 |

## 8. 验收边界和建议

建议按这个范围接入数据。当前方案不需要第二个全站浏览量排序索引、不需要搜索服务、不需要图片存储。名称索引把每次接近 96 万行的无索引查找变为小范围读取，收益足以覆盖约 69.3 万索引项的初始化和每月约 8,500 项维护。

上线核验重点是索引是否被使用、游标是否保持范围扫描、快照是否仅在后台刷新、每日浏览量水位是否与快照一起发布。初始上线记录实际 `rows_read/rows_written/size_after`；CPU、日志事件数及新增存储在运行后替换假设。若新增模糊搜索、名字规范化、实时榜单、更多日志、异常自动重试或直接展示九宫格，需要更新模型。

本轮只读审计自身已取得 meta 的查询合计 **963,668 行读取、0 行写入**，全超额读取等值 **$0.000963668**。成本来自一次登记表聚合和小规模计划/查询检查；未生成索引或后台快照。生产访问使用已有只读 SQL 凭据，没有运行浏览器交互或新增测试代码。
